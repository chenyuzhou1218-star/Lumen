# 评测基准（bench）

用固定场景给**长期记忆**和**推理逻辑**打分，让每次改动都能用数字说明有没有效果，而不是凭感觉调权重、改提示词。

```bash
.venv/Scripts/python -m codedoctor bench                                   # 跑全部，打印报告
.venv/Scripts/python -m codedoctor bench --suite memory                    # 只跑记忆
.venv/Scripts/python -m codedoctor bench --out bench/results --name <名字>  # 写 JSON + Markdown
.venv/Scripts/python -m codedoctor bench --suite memory --embedding-config <你的配置.toml>  # 加测 M6（用你选的嵌入模型）
```

不需要项目配置，也**不调用任何真实模型**：每个场景都在临时复制的 `samples/shop-coupling` 上运行，跑完即删。结果里不含 ID、时间戳和耗时，所以同一份代码跑两次，结果文件逐字相同；改了代码之后用 diff 就能看出分数变化在哪。

## 目录

| 路径 | 内容 |
|---|---|
| `bench/scenarios/memory/*.json` | 记忆场景：一段"历史"+ 一组带标准答案的问题 |
| `bench/scenarios/reasoning/*.json` | 推理场景：图谱分析（static）和端到端任务（agent） |
| `daemon/codedoctor/bench/policies.py` | 脚本 Agent 的行为（"仔细"和"犯典型错误"两类） |
| `daemon/codedoctor/bench/memory.py`、`reasoning.py` | 评分 |
| `bench/results/` | 已记录的结果 |

## 记忆召回怎么评

**历史**：按顺序重放到数据库里：带真实代码证据的主张、Guardian 复查（证实或推翻）、任务结束（与 Agent 运行时用同一段代码写摘要和主张笔记）、`remember` 式笔记、代码修改。场景 `shop-history` 模拟了 5 次过去的调查，包括一个被推翻的错误线索、一个被取代的主张、一次让某个结论过时的代码修改，以及 8 条无关笔记。

**问题**：每题写明三类笔记：

- **relevant**：应该被召回的笔记，按组写；组里任意一条出现在前 8 条就算这组命中。
- **untrusted**：不能被当成事实展示的笔记，即已推翻或已过时的结论。
- **forbidden**：读者无权看到的笔记，例如别的 Agent 的私有记忆。

**四种配置逐级累加**，对比每一步的作用：

| 配置 | 含义 |
|---|---|
| ADR 0003（本批之前） | 纯文字匹配，不看主张状态，没有按主张拆分的笔记 |
| +M1 主张状态 | 召回时读取主张当前状态（警示标记 + 加减分） |
| +M3 按主张拆分 | 每个主张一条笔记，摘要降权 |
| +M2 耦合回忆（当前） | 沿耦合图谱扩展 |
| +M6 按意思回忆 | 加上向量检索（[ADR 0007](../docs/adr/0007-semantic-recall.md)）。**只有**传了 `--embedding-config <你的配置文件>` 才会跑，用的是你在那份配置里选的嵌入模型；样例场景的笔记会发送到那个服务。不传时报告写"未评测"。 |

**指标**：

| 指标 | 含义 |
|---|---|
| recall@8 | 前 8 条里命中的 relevant 组所占比例 |
| MRR | 第一条正确笔记排名的倒数，取平均 |
| 未警示的不可信笔记 | untrusted 笔记出现在前 8 条且**没有**任何警示（已推翻 / 过时 / 撤回 / 代码已改）的次数，**应为 0** |
| 不可信笔记排在正确笔记前 | 即使带了警示，排在第一条正确笔记前面也会误导小模型 |
| 越权可见 | forbidden 笔记出现的次数，**必须为 0** |

## 上下文怎么评（`--suite context`）

预算 6000 token（其中约 2700 是每次请求都要带的工具说明，余下约 3300 留给对话，接近本地小模型）的长任务：先提交两个主张、撤回一个，再读完一批文件并重读几个。同一任务分别用"M5 之前"和"M5（当前）"两种上下文策略跑，统计：超出预算的请求数、改写上下文的次数（影响本地模型的前缀缓存）、总输入字符、最后一次请求里证据 ID 和主张当前状态还在不在。详见 [ADR 0008](../docs/adr/0008-context-management.md)。

## 推理怎么评

**图谱分析（不用模型）**：样例项目里 7 个埋设缺陷的检出率和在风险列表里的排名，共同根因分析是否把共同根源排在第一，影响分析能否跨过客户端 / 服务端边界。

**端到端任务**：脚本 Agent 按策略跑完整个任务（单 Agent 或集群），然后**只根据数据库里留下的东西打分，不看回答的措辞**：

- **结果**：
  - 根因：1 = 有经过验证的因果主张指向真正的根因；0.5 = 只有未验证的；0 = 没有。
  - 错误事实：被验证为成立、却指向错误线索的主张数。
  - 覆盖：必须涉及的实体中，出现在主张或回答里的比例。
  - 成本：模型调用次数和 token。
- **推理缺陷**：交付答案时存在的推理错误：
  - `unclaimed_conclusion` 没有主张就下结论
  - `unsupported_conclusion` 结论没有一条经过验证
  - `false_lead_asserted` 主张指向已知的错误线索
  - `competing_open` 竞争假设没有排除
  - `chain_gap` 主张链没连到症状
- **系统指出**：系统自己有没有把这些缺陷指出来。报告的 `body.reasoning_checks` 里列出某项检查才算指出；这是留给推理批次（R1 / R2）填写的接口。没有对应缺陷却报了，算误报。

**用脚本 Agent 时测的是系统，不是模型。** 同一种行为下，系统能不能发现推理错误、发现了会不会误报。等你指定真实模型后，同一批场景测的就是模型：它能不能找到根因、会不会把猜测当事实交付。目前的运行器还不支持真实模型，需要再加一个读取你的项目配置的选项（模型仍由你指定）。

### 基线暴露的问题（按影响排序）

1. **用 `remember` 记下的错误结论永远不会被标"已推翻"**（未警示 3 次，p1 / p9 / p11）。`remember` 只能引用证据、不能挂主张，所以主张被推翻后，这条笔记照样像事实一样被召回。M1 只覆盖了系统写的笔记。
2. **被推翻的笔记靠名字匹配或耦合关系仍排在前面**（排在正确笔记前从 1 次变成 3 次）。例如 p11 问 finishMatch，排第 1、2 的是两条已被推翻的错误结论。推翻的扣分（−0.3）比名字命中的加分（+0.6）小。
3. **推理缺陷系统一个都没指出（0/7）**。"跳到错误结论"的策略把错误根因当作 `done` 交付，没有任何提示。这正是 R1 / R2 要解决的。
4. **种子识别漏掉接口路径和状态名**：p8 问 `/api/session/reconnect` 和 gold，一个种子都没找到（RR 0.33）。
5. **跨语言召回差**：p9 用英文问，笔记是中文（RR 0.2），需要 M6 向量检索或双语处理。
6. **被取代的主张笔记和取代它的新笔记同时出现**（p3：旧的 c4 排第 1，新的 c5 排第 3），内容重复。
7. **共同根因的排序偏向状态**（cc2：期望 add_gold，实际排第 7；排第 1 的是一个结算计数字段）。另外 gold_changed 缺陷在风险列表中排最后（11/11）。

另外：M1 单独几乎没有作用（MRR 0.649 → 0.635），因为 M3 之前，只有混合了多个主张的摘要笔记带主张引用；M1 要和 M3 一起才有效果。

## 局限

- 规模小：1 个记忆场景（11 题）、1 个图谱场景、2 个端到端场景（4 次运行）。数字只能看方向。
- 用同一批题调权重会过拟合。之后调参时要留一部分题不参与调参，专门用来检验。
- 端到端场景的"错误"是人为设计的典型错误，不代表真实模型的错误分布。
