## 下一步建议

用户定的重点是长期记忆和推理逻辑。已完成：M1 → M3 → M2 → 评测基准 → M6 → M5（2026-10-25 用户要求先做 M6、再做上下文优化）。然后集群加强（ADR 0009）。2026-10-25 晚：并入 ChatGPT 的业务集群与持续推演，补全界面，修复它两份审查指出的问题（ADR 0011）。接下来：R1 → R2 → R3 → R4 → M4。

注意（R5 之后）：上下文预算现在计入工具说明并且是硬上限。本地小模型只有 2k–4k 上下文时，系统提示加工具说明就要约 3.3k token，`context_budget_tokens` 必须按模型真实上下文设置；长任务在小预算下会以“预算”原因停止。可做第三级压缩（合并最老的整步）。每做完一项都重跑 `codedoctor bench`，把结果和基线对比。

M6 要发挥作用，需要用户选一个嵌入模型（本机 Ollama 的多语言嵌入模型最安全，但用户电脑内存紧张，本地模型的拉取和运行由用户决定）。

基线暴露的、尚未排入上面顺序的问题（详见 bench/README.md）：`remember` 写的笔记不能挂主张，被推翻后不会被标出；被推翻的笔记降权不够；种子识别漏掉接口路径和状态名；被取代的主张笔记重复出现；共同根因排序偏向状态。

1. R1 鉴别诊断：同一症状的竞争假设成组，每个须有证伪测试；系统指出区分力最强的下一步检查；仍有未排除的竞争假设时不能把其中一个当结论交付。
2. R2 因果链完整性：症状 → 机制 → 根因每环一个主张，系统标出缺环、仅推测环、依赖已推翻主张的环。
3. R3 故障模型推演、R4 主张矛盾检测、M4 记忆整理。
4. 仍待做：真实模型联调；运行时追踪 SDK → ingest → 链路组装 → 断点判定。
