# 对比报告：Code Doctor 与 WorkBuddy（DeepSeek Flash 1017）

日期：2026-10-30 至 10-31。所有数字都来自真实运行，打分脚本和运行记录在 `bench/trials/` 和 `D:\private\cd-trial\results.jsonl`。

## 怎么测的

- **三个测试仓库，共 37 个耦合 bug**
  - chainshop（网店，13 个）
  - 图书馆借阅（13 个，其中一部分没人报告过）
  - 健身房约课小网站（11 个，前后端都有）
- **同一个模型**：DeepSeek V4.1 Flash 1017。
- **同一份任务描述**：用户投诉加上"找出所有缺陷（包括没人报告的）并修好"。
- **打分**：每个仓库有一个独立的打分脚本，逐个检查 bug 是否真的修好。打分不看模型自己说了什么，也不看仓库里的测试。
- **WorkBuddy**：由用户在它的图形界面里手动操作，用免费的 Deepseek-V4.1-Flash（积分）。它界面上不显示 token，所以 token 数没有。用时是按它修改文件的时间估算的。

## 结果

| | chainshop | 图书馆 | 健身房 | 合计 | 总用时 | 总 token |
|---|---|---|---|---|---|---|
| **Code Doctor 6 人（2 首脑 + 2 组）** | 13/13 | 12/13 | 11/11 | **36/37** | **798 秒** | **约 194 万** |
| Code Doctor 双人互检（2 人） | 13/13 | 12/13 | 11/11 | 36/37 | 855 秒 | 约 217 万 |
| WorkBuddy（1 个 agent） | 13/13 | 11/13 | 11/11 | 35/37 | 每个约 8–9 分钟（估算） | 界面不显示 |
| Code Doctor 20 人（补位版） | 13/13 | 12/13 | 10/11 | 35/37 | 930 秒 | 约 454 万 |
| Code Doctor 20 人（旧版，按文件拆分） | 4/13 | 6/13 | 9/11 | 19/37 | 1324 秒 | 约 498 万 |

（Code Doctor 的用时和 token 是三个仓库加起来的总数。）

## 结论

- **谁更准**：Code Doctor 6 人和双人互检都是 36/37，WorkBuddy 35/37。WorkBuddy 多漏了图书馆的"网页借书字段对不上"。三方都漏了"同一本书不能借两次"，这条规则 README 和投诉里都没写。
- **谁更快**：Code Doctor 6 人最快，三个仓库一共 798 秒。WorkBuddy 每个仓库约 8–9 分钟（按文件修改时间估算），Code Doctor 是每个 3–5.5 分钟。
- **谁更省**：Code Doctor 6 人比双人互检少用约 10% 的 token。WorkBuddy 的 token 数看不到，没法比。
- **最烂的**：旧版 20 人。它把耦合的代码按文件拆给很多人，每人只看到一段，还把预算花在读代码上，结果只修对 19/37，token 却是 6 人的 2.5 倍。

## 20 人为什么一开始很差，后来怎么改的

1. **耦合代码不能按文件拆。** 现在改成由一组主力修全部代码，它自己就相当于一次双人互检，保证了下限。
2. **多出来的人改做侦察。** 侦察兵按业务场景写测试，查出主力漏掉的 bug。系统会把每个侦察测试拿到原始代码上再跑一遍，在原始代码上也能通过的测试等于没复现出问题，会被打回去重写。
3. **备选组浪费预算。** 一开始让两组各在一份副本里重修一遍，三轮全输给主力组，还花掉 28% 的预算。现在改成补位组：侦察兵查出的 bug 交给空闲的补位组，直接在主项目里修。
4. **系统兜底。** 所有人都停下后，如果还有原来能过、现在挂掉的测试，系统会自动撤回改坏它的那处修改，保证代码不会比原来更糟。

## 还没确定的

- 每个配置在每个仓库只跑了一次。36 和 35 只差 1 个 bug，在随机波动范围内。要得出"谁更强"的可靠结论，需要更难的仓库，每种配置跑 3 次取平均。
- WorkBuddy 的真实用时和积分消耗，需要从它的界面上补录。
- 实际花了多少钱：从这一版起，每次运行会记录 DeepSeek 返回的缓存命中 token 数。从运行记录模拟看，每次请求有 80%–90% 的开头和上一次相同，可以走缓存。
