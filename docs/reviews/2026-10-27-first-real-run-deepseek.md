# 第一次真实模型试跑：DeepSeek，双人互检（2026-10-27）

## 设置

- 示例项目：`D:/private/cd-trial/shop-orders`（不在游戏文件夹里；16 个文件，Python 服务端 + JS 客户端）。项目里埋了 4 个跨模块 bug，代码注释里没有任何提示；答案只留在仓库外。
  - B1（问到）重复扣款：`web/api.js` 超时 3 秒后连 POST 也重发，`server/checkout.py` 没有幂等键。
  - B2（问到）改价后仍按旧价：`catalog` 用 `price:{sku}` 缓存，`admin.set_price` 删的是 `price_{sku}`；自带测试只断言数据库，所以测试是绿的。
  - B3（没问到）优惠券单位：`promo.COUPONS` 是元，却从"分"的小计里直接减。
  - B4（没问到）`refund()` 退钱但不把库存放回去（`cancel()` 会放回）。
- 问题（只描述症状）："网络慢的时候，有用户反馈被扣了两次钱；另外管理员改了价格之后，结账时有时候还是按旧价格收钱。请找出原因。"
- 2 个 agent（worker-1 + guardian-1），都用 deepseek-chat（用户在自己配置里选的模型）；整个调查共享 30 万 token 预算；不能运行命令。
- 命令：`codedoctor run --config dual.toml --agent worker-1 "…"`。

## 六轮结果

| 轮次 | 结果 | 找到 | 结论被 guardian 证实 | worker 输入 / 输出 token | 发现的问题 → 改动 |
|---|---|---|---|---|---|
| 1 | 预算用完，没有回答 | B1、B2 都推理对了，但没有一条结论入库 | — | 297k / 9k | `submit_claim` 只给模型看 `{"claim": object}`，7 次草稿全被拒（凭空写出 `root_cause`、`code_only`、`primary`、纯文字的 subject）；另有 5 次调用花在被禁用的 `run_command` 和没有首脑就用不了的业务调查工具上 → 工具展示完整格式、接受明确的简写、报错给出真实实体 id；用不了的工具不再发给模型 |
| 2 | 预算用完 | B1、B2、B3，另有测试漏洞、结账非原子 | 0（guardian 没有预算） | 304k / 12k | 4 条结论一次通过；worker 用光了共享预算 → 回答用户的 agent 给 guardian 留 30%，用到 60% 时提醒收尾，到线后要求不用工具直接回答 |
| 3 | 有完整回答，但被挡下 | B1、B2、B3；退款列为"值得单独排查" | 0（命令行在 guardian 开始前就退出了） | 244k / 10k | 命令行等复查结束再退出；预算提醒里要求先决定自己报的异常 |
| 4 | 被挡下 | B1、B2、B3 | 0（guardian 读完全部文件就没预算了） | 234k / 8k | 最后那次回答本身要重发整个上下文 → 按"再发一次请求"预估，提前进入回答 |
| 5 | **完成** | B1、B2、B3；异常由 worker 自己定为"立即修复" | 0（guardian 又先通读了整个项目） | 192k / 9k | guardian 也会收到提醒：大约只剩两次请求的预算时，必须对每条结论下判断 |
| 6 | **完成** | B1、B2、B3 | **2/2 已证实** | 224k / 8k（guardian 69k / 2k） | 模型漏掉或多包一层 `claim` → 两种都接受 |

B4 一直没有找到（第 3 和第 6 轮都提到了退款流程，但说的是别的风险）。

## 花费

第 6 轮两个 agent 合计约 29 万输入 token、1 万输出 token，22 次模型调用，用时约 1 分钟。每次请求都会把之前的对话重新发一遍，DeepSeek 会缓存重复的前缀，所以实际费用比按全价算要低。具体金额以 DeepSeek 后台账单为准。

## 还没做

- 6 个 agent 的小集群：双人互检已经找到了问到的两个 bug，所以没有跑。
- 每条请求都带约 4800 token 的工具说明，其中 `submit_claim` 占 862；之后可以考虑精简。
- `remember` 的实体字段还不接受 `path#name` 简写（第 2 轮有一次失败）。

# 第二个项目：20 个 agent 的集群（同一天）

- 示例项目：`D:/private/cd-trial/gym-booking`（健身课预约，13 个文件）。
  - G1（问到）超员：`stats` 按课程名计数，`classes.remaining` 却按课程 id 查，永远是 0。
  - G2（问到）取消后又扣课时：`cancel` 把取消者当成 `waitlist.promote` 的 `payer`。
  - G3（没问到）`policy.hours_until` 用 `timedelta.seconds`，丢掉了整天，所以提前几天取消也算"临时取消"。
  - G4（没问到）课前提醒拿本地时间和 UTC 比较，差了 8 小时。
- 20 个 agent：2 个首脑 + 9 组 worker/guardian，都用 deepseek-chat；整个调查封顶 60 万 token；持续监测关闭。

| 轮次 | 找到 | 证实 | 合计 token | 发现的问题 → 改动 |
|---|---|---|---|---|
| A | G1、G2、G3，并指出两者叠加后取消一次净亏 2 课时 | 0 | 78 万（超过上限 26%） | 逻辑首脑被咨询时把整个项目读了一遍（40 万）；guardian 没有预算 → 除复查外的子任务一共只能用到预算的 70%，每个子任务最多用 20%，用到时被要求直接交出结果；逻辑首脑被咨询时简短回答 |
| B | G1、G2、G3（4 个 worker 和逻辑首脑互相印证） | 0 | 78 万 | 逻辑首脑降到 13 万，但 5 个 agent 同时请求，各自只看已经返回的用量，一起冲过了上限 → 已发出、还没返回的请求按预计大小计入预算（`orchestration.inflight`） |

只有 6 个 agent 实际干了活（2 个首脑 + 4 个 worker），另外 14 个一直闲着，没有调用模型。G4 两轮都没找到。B 轮之后的改动还没有用真实模型验证过。

结论：
- 耦合紧的小项目，交给少数人最好：双人互检速度最快、花费最低、修得最准。
- 人多只适合彼此独立的文件。系统会按 import、接口路径和耦合图谱自动分组。
- 每次修改后由系统直接跑测试，这是提分最多的一项改动，而且不花 token。
