# ADR 0008：上下文优化（M5）

- 状态：提议（待审查）
- 日期：2026-10-25
- 作者：Claude
- 用户要求：M6 之后做上下文优化。
- 目标硬件：用户的电脑是 AMD Mendocino 核显、内存紧张，本地模型的上下文通常只有 2k–8k token。

## 原来的问题

1. **关键事实被挤掉**：上下文超出预算时，最早的工具结果被删减，只保留 `evidence:` 和 `file:` 两类行。"主张已提交（clm_…）""已撤回"这类系统写的结果也一起删掉了。长任务做到后面，模型不再知道自己提过哪些主张、现在是什么状态。
2. **上下文经常被改写**：每一步只删减到刚好低于预算，于是任务后期几乎每一步都要改写上下文中间的内容。本地模型（llama.cpp / Ollama）靠前缀缓存（KV cache）加速，中间一改，整段都得重新计算。在弱 CPU 上这正是最慢的地方。
3. **同一个文件读两次就占两份位置。**
4. **召回的记忆不限长度**：8 条任务摘要，每条最多 6000 字，可能一次塞进约 1.6 万 token。
5. **工具输出不看预算**：`read_file` 一次最多返回 400 行，不管模型的上下文有多小。
6. **日志还原不了真实请求**：删减会改写已经发送过的消息，但日志只记录每次请求新增的消息，所以无法还原模型实际看到的内容。

## 决定

### 工作记忆（系统维护，不靠模型自己写）

每次请求时，系统从数据库生成一段"工作记忆"，放在请求的**最后**：

- 本任务及其子任务的主张和**当前**状态：已证实 / 未验证 / 过时 / 已排除（推翻或撤回）。数据从库里读，所以 Guardian 刚推翻的结论也会立刻反映出来。
- 已收集的证据 ID（最新的在前）。放不下的旧证据只列"文件 行范围"，并说明重读同样的行就能得到同一个 ID。
- 本 Agent 保存的笔记、子任务状态，以及有多少旧结果被删减。
- 整段用 `wrap_untrusted` 包起来，作为信息，不作为指令。

**只在有用时才附上**：上下文用量超过预算一半、有内容已被删减、有主张的状态已经不是"未验证"、或者有子任务。短任务、空间宽裕时不附加，没有额外开销。

放在请求最后，是为了不破坏前缀缓存：前面的对话内容保持不变。

### 一次删减到位

超出预算时，直接删减到预算的 70%，而不是每一步只删一点。如果所有工具结果都删减过了还是放不下，就进入第二级：把这些删减后的短条目再压成一个固定标记。这些条目里的证据 ID 和主张都已经在工作记忆里，所以不会丢失。

删减时保留的系统行增加了"主张已提交""笔记已保存""子任务已分派"三类。

### 相同结果不重复

如果一个工具结果和上下文里一条**仍未被删减**的结果完全相同，就改为一句"与上面那次结果相同"，保留证据 ID。日志里仍然保存完整原文。

### 按预算控制召回和工具输出

- 任务开始时召回的记忆最多占预算的 15%。超长的笔记会截短，并提示可以用新工具 `read_note <id>` 看全文。放不下的笔记按排名丢弃，并说明还有多少条没显示。
- 工具输出上限为预算的 25%（在 2000 到 12000 字之间）。`read_file` 按这个上限决定读多少行，**证据 ID 只覆盖实际显示给模型的那些行**，避免引用模型没看到的内容。

### 日志能还原每一次请求

`model_request` 的记录从"新增消息列表"改为：

```json
{"messages": [...新增的消息], "rewritten": {"序号": "改写后的内容"}, "working_memory": "..."}
```

`rewritten` 只记录在**之前的请求里已经发送过**、这次被改写的消息；新增消息本身已经是改写后的样子。断点续跑时，按这三部分重建对话。旧格式（纯列表）照样能读。

### 策略可以对比

以上所有行为都集中在 `ContextPolicy` 里，`BEFORE_M5` 还原旧行为，供评测对比。

## 评测（`codedoctor bench --suite context`，脚本模型）

场景：预算 2000 token 的长任务。先提交两个主张并撤回其中一个，然后读完 10 个文件，再重读 3 个。

| | M5 之前 | M5 |
|---|---|---|
| 超出预算的请求 | 3 / 19（峰值 1.15 倍） | **0 / 19**（峰值 0.78 倍） |
| 改写上下文的次数 | 3 | **2** |
| 总输入字符 | 86,057 | **72,025（−16%）** |
| 最后一次请求里仍写明主张当前状态的比例 | 0% | **100%** |
| 证据 ID 仍完整出现 | 100% | 8% |
| 证据可找回（完整 ID 或"文件 行范围"） | 100% | 100% |

**代价**：

- 预算很小时，旧证据只剩"文件 行范围"，要引用时得重读一遍，多一步。
- 默认预算（64k）下，4 次端到端推理运行的 token 总数从 27,637 增加到 28,321（+2.5%），来自调度首脑跟踪子任务时附加的工作记忆。

## 不在本次范围

- 删减后的内容由模型写摘要（"逻辑保真压缩"）：需要额外调用模型，留给之后的压缩 Agent。
- 按真实 tokenizer 计算 token：仍按每 token 3 个字符粗估。

## 测试

- `tests/daemon/test_context.py`（7 项）：
  - 工作记忆反映主张的当前状态、写入日志，短任务不附加；
  - 一次删减到低水位、改写次数更少，并能从日志逐条还原每一次请求；
  - 相同结果不重复；
  - 工具输出随预算变化，且证据范围与显示内容一致；
  - 召回限额和 `read_note`、`read_note` 不能读别人的私有笔记。
- `tests/daemon/test_bench.py`：上下文评测。
- 改了 3 个旧测试：它们原来假定"最后一条消息就是工具结果"。
- 测试用的脚本模型改为记录每条消息的副本：删减会原地修改消息对象，原来的记录会跟着变，和当时实际发送的内容对不上。
- 全部 454 项通过。

## 更正（2026-10-25，ChatGPT 审查 R5 之后）

上面的评测表有误：当时计算请求大小没有包括**每次请求都要带的工具说明**（general 角色约 2,700 token）。按 ChatGPT 运行时审查 R5 修正后，有两点变化：

- 预算现在把工具说明算进去，并且是**硬上限**：删减之后整个请求仍然放不下，就不发送，停止并说明各部分各占多少（[ADR 0011](0011-cluster-ui-and-review-fixes.md)）。
- 评测场景的预算改为 6000 token（工具说明约 2,700，留给对话约 3,300）。重新测量的结果如下：

| | M5 之前 | M5 |
|---|---|---|
| 超出预算的请求（含工具说明） | 3 / 19（峰值 1.12 倍） | **0 / 19**（峰值 0.89 倍） |
| 改写上下文的次数 | 0（从不删减，直接超出） | 3 |
| 总输入字符（含工具说明） | 270,511 | **256,154（−5%）** |
| 最后一次请求里主张当前状态仍可见 | 100% | 100% |
| 证据 ID 完整保留 / 可找回 | 100% / 100% | 83% / 100% |

所以，"主张状态保留 0% → 100%" 那条结论**不成立**：那是漏算工具说明造成的。M5 在这个场景里真正的效果是：

- 不再悄悄超出预算；
- 删减更少地改写上下文中间部分；
- 总输入略少。

另外，预算很小时，长任务现在会停在"上下文已满"并说明原因，而不是带着超长的请求继续发送。改进方向是第三级压缩：把最老的整步（模型调用 + 工具结果）合并掉，那些步骤的信息在工作记忆里都有。这一项还没做。
