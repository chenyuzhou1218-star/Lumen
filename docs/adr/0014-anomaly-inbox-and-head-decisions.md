# ADR 0014：零遗漏异常上报、首脑决策与集群调度设置

- 状态：提议（待审查；用户自己测试）
- 日期：2026-10-26
- 作者：Claude
- 用户要求：多 Agent 集群是最重要的。按用户给的设计图做：零遗漏上报、理性完美主义（微异常深度推理）、首脑不只有"修复/忽略"两种决策、异常影响深度、细节审查清单、首脑的五种工作状态、"首脑不准轻易宣布完成"、监督发现问题后的完整指挥链、基础 / 协作 / 高级集群三种调度、最多 19 对执行/监督 + 2 个首脑 = 40 个 Agent。界面简洁，照设计图。

## 1. 零遗漏上报：异常收件箱

新工具 `report_anomaly`：执行者、调查员、监督者、单 Agent、逻辑首脑都能用。任何异常都要报：崩溃、数据库错误、偶发的流程失败、按钮点不了、少一个像素或图标、文字内容或位置不对、动画少一帧、日志里不寻常的警告、怀疑的耦合问题。只是怀疑没看到的，标为 `hypothesis`（界面显示"假设，待验证"）。

- 必须引用看到它的证据 ID；只有标为假设时才可以没有证据。证据 ID 由系统校验。
- **永不删除**。同一次调查里同类、同标题、同位置的重复异常合并为一条，每次出现都作为一条"出现记录"保留各自的证据。
- **重大的立即唤醒**：崩溃、数据错误、流程失败，或者表面表现"大"的异常，会立刻给逻辑首脑建一个评估任务；调度首脑正在 `wait_for` 时也会马上醒来，不用等最慢的子任务。
- **细小的保证进入下一轮审阅**：调度首脑每次拿到子任务结果（`wait_for`）、查看状态（`task_status`）或准备交付时，系统都会确认逻辑首脑有一个评估任务在处理未决策的异常。
- **类似症状再次出现**：新异常和以前"加入待办 / 标记待确认"的异常（任何一次调查）指向同一个文件或实体时，旧异常被标为"需要重新评估"，交给逻辑首脑判断是否有共同根因。

表：`anomalies`（每条一行，JSON 文档带全部历史）。

## 2. 首脑决策：四种处理，加上程序算出的优先级

逻辑首脑（单 Agent 模式下是它自己）用 `decide_anomaly` 决策，先要回答"微异常深度推理"的五个问题，缺一个系统就拒绝：

1. 它原本应该存在 / 是这样吗？（设计、历史版本）
2. 是什么产生的？（遮挡、渲染失败、某个状态没触发……）
3. 它是否参与点击、事件监听、碰撞或其他逻辑？
4. 其他组件是否用了同样的渲染 / 状态 / 逻辑？
5. 修改它可能影响什么？

决策：**立即修复**（证据明确且能安全处理）/ **扩大调查**（可能有更深的耦合故障）/ **加入待办**（真实但当前影响低）/ **标记待确认**（还不能判断是不是预期设计）。

**异常影响深度**：上报时给出"表面表现"大小，首脑给出"潜在耦合影响"大小，由程序（不是模型）换算处理方式：

| 表面表现 | 潜在耦合影响 | 处理方式 |
|---|---|---|
| 小 | 小 | 记录并安排局部修复（P3） |
| 小 | 大 | 优先进行系统级调查（P1） |
| 大 | 小 | 优先修复直接故障（P1） |
| 大 | 大 | 立即组织跨模块调查与独立验证（P0） |

"潜在影响大"必须有证据，或者有明确的假设加证伪方法，否则系统拒绝——不能因为 AI 想象出复杂故事就无限消耗 token。

`resolve_anomaly`：只有引用一条状态为"成立"（经过监督者独立复查）的结论，或者确认是预期行为并给出证据，才能标为已解决。

## 3. 监督发现问题之后的完整指挥链

1. 监督者（或执行者）发现疑似问题 → `report_anomaly`，附文件行号、证据、影响范围。
2. 重大的立即唤醒首脑；逻辑首脑做耦合分析并决策。
3. "立即修复 / 扩大调查"由调度首脑 `delegate(anomaly=…)` 派出。**复核不交给原来的执行者**：异常来自哪个执行者的工作（监督者上报的，就是它所监督的那个），系统就不允许把它派回给这个执行者（还有别的执行者时），`"any"` 也会自动避开。
4. 新执行者做完，由它的监督者再次独立复查。
5. 结论"成立"后，调度首脑 `resolve_anomaly`；双首脑汇总交付。

（"在隔离分支修改代码"需要写文件和 Git 分支隔离，这部分还没开放，见 STATUS。）

## 4. 首脑不准轻易宣布完成

- 两个首脑的工作记忆里，系统每一步都会附上**未解决问题清单**：未决策的异常、需要重新评估的异常、决定了"修复 / 扩大调查"但还没解决的异常、未确认的清单项、未撤回的异议。
- 调度首脑（单 Agent 也一样，但只看它自己未决策的异常）想给出最终回答时，系统先做**交付审查**：还有未完成的子任务、未决策的异常、没解决的后续、没确认的清单项，就把它退回去继续做，最多退回 2 次。
- 2 次之后它的回答照常给出，但**系统在回答末尾自动附上细节审查清单和异常统计**，哪些没做完一目了然。
- **还有异常没人决策时不能交付**：结果标为"被拦下"，列表交给用户决定（和首脑异议的处理方式一样）。

## 5. 细节审查清单

每次集群调查默认 6 项：功能流程和业务状态、跨模块耦合与连锁影响、UI 元素完整性与显示位置、不同分辨率和窗口尺寸、断网/退出/并发等边界条件、长期运行与异常恢复。首脑可以加项，也可以写明理由标为不适用。

**完成状态由证据自动确认**：Agent 只能把结论和证据挂到某一项上（`checklist_update`）；只有挂上的结论状态是"成立"（监督者独立复查过）时，这一项才算完成。结论之后被推翻，这一项会自动变回未完成。

## 6. 首脑的五种工作状态

监听待命（没有任务，不调用模型）/ 审核报告（等待和阅读结果）/ 主动反思（分析图谱、决策异常、推演）/ 下达指令（分派、咨询、异议）/ 交付审查。由系统从首脑最近的动作推出来，显示在 Agent 集群页。

## 7. 调度设置：基础 / 协作 / 高级集群

"模型与 API"页新增"Agent 调度设置"：

- **基础**：只用单 Agent，`[cluster] mode = "basic"`，输入框不再出现"多 Agent 集群"。
- **协作**：双首脑 + 执行/监督对，`mode = "collab"`，一次只运行一个子任务（第二个 `delegate` 会被要求先 `wait_for`）。
- **高级集群**：双首脑 + 1–19 对，`mode = "advanced"`。勾选"按需唤醒"（`parallel`）后多对同时工作；勾选"持续监控"即开启已有的持续推演。
- 滑块调整对数：增加的对**没有模型**，保存前必须选（可以在表里逐个选，也可以用"用这个模型"一次给多个选同一个——仍然是用户选，系统不替你选）。减少时移除编号最大的几对，历史记忆保留。
- 上限：首脑、执行者、监督者合计不超过 40（2 + 19 对）。单 Agent 不算在集群里。
- 页面附"两种模式的真正区别"对照表。

**上下文与记忆**：设计图里"每个 Agent 10M、首脑 200M"的目标，按实际情况显示：一次请求能发给模型的内容受模型本身限制（常见 64k、128k、1M），这是每个 Agent 的工作上下文，要和模型的真实上下文一致；更大的长期上下文靠本机的长期记忆、证据库和按需精确召回实现，原始记录不设上限、不会因为压缩丢失。界面上不显示做不到的数字。

## 8. 界面

- **Agent 集群页**：集群结构（Core A 逻辑首脑、Core B 调度首脑，下面是每一对执行者 ⇅ 监督者，每个都有实时状态和所用模型；底部是共享证据与系统耦合图谱）、首脑的五种工作状态、整个项目的异常收件箱、原有的持续推演和业务实验。
- **调查页**：异常与首脑决策（状态、类型、重大、假设、出现次数，展开看观察、位置、证据、五个问题的回答、影响依据、后续任务、解决依据）、异常影响深度矩阵、细节审查清单（进度条，"仍有未完成的检查项目"）。
- 只读：界面不能替首脑决策。

## 接口

`GET /anomalies?root_task_id=`、`GET /checklist/{root_task_id}`（只读）。
