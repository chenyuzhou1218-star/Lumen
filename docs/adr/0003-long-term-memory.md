# ADR 0003：长期记忆

- 状态：提议（待审查）
- 日期：2026-10-24
- 作者：Claude

## 目标

让每个 Agent 拥有独立、可以长期增长的记忆，并且**无论怎么压缩，原始证据都能精确回查**。原生上下文窗口由模型和硬件决定；这里解决的是上下文之外的长期记忆。

## 决定：两层结构

### 第一层：journal（完整层）

- 记录一切：收到/发出的消息、每次模型请求与响应、每次工具调用与结果、状态变化、预算停止、停滞停止、模型切换。
- **只追加，不修改，不删除，永远不会被摘要替代。**
- 大内容放进 blob 存储（按 sha256 寻址），条目里只存哈希。`original()` 能取回完整原文。
- 模型请求只存"本次新增的消息"，按顺序拼接即可还原每次请求的完整上下文，避免重复存储。

### 第二层：notes（检索层）

- 每条笔记有类型（fact / decision / observation / todo / summary）、关联实体、证据 ID、主张 ID、代码版本、任务 ID。
- **必须有来源**（journal 条目或其他笔记的 ID），否则写入失败。所以任何摘要都能追溯到原文。
- 更正不删除旧笔记，而是标记 `superseded_by`：旧笔记不再出现在检索结果中，但仍可读取。
- 可见范围：`agent`（仅自己）或 `project`（共享，读取需配置允许 `shared_read`）。每个 Agent 有独立记忆。
- 每个任务结束时自动写一条 `summary` 笔记（结果、摘要、证据、主张），所以下一次任务能想起来上一次做了什么。
- 任务开始时，运行时用任务标题和说明检索记忆，把最相关的 `recall_k` 条放进提示（标记为不可信数据，并提示"使用前先验证"）。

### 检索方式

SQLite FTS5 + **trigram 分词**：
- 文件路径、行号、函数名、标识符（`shop.py:47`、`inventory_version`）作为子串精确匹配。普通的分词检索会把这些拆碎，trigram 不会。
- 中文无需分词器：3 个字及以上走 trigram 索引；2 个字的词（"金币"、"超时"）走 LIKE 匹配。
- 按"查询词命中比例"排序，置顶笔记加分，同分时按时间排。

## 容量

SQLite 单库可以承载数十 GB。200M token 的文本大约在 1 GB 量级，对 FTS5 来说没有问题。真正的限制是检索质量，而不是存储量。

## 后续（不在本次范围）

- 可选的向量检索（本地嵌入模型），作为 trigram 之外的第二路召回。
- 逻辑保真压缩 Agent：把大量 journal 压缩成 summary 笔记，由检查 Agent 用原文抽问核对，确认没有丢失核心事实。数据结构已经就绪：summary 必须引用来源。
- 记忆与代码版本的联动（代码修改后，标记与旧版本绑定的笔记"可能过时"）。
- 记忆与主张状态联动、按主张拆分记忆、沿耦合图回忆：见 [ADR 0006](0006-memory-claim-status-and-coupling-recall.md)。
