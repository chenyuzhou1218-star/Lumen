# ADR 0011：业务调查的桌面界面，以及 ChatGPT 两份审查的修复

- 状态：提议（待审查）
- 日期：2026-10-25
- 作者：Claude
- 背景：ChatGPT 实现了业务集群后端（ADR 0010，提交 `da9db15`），以及持续推演和可调整的集群规模（`1494b1a`）。它的额度用完时，持续推演部分已通过测试，但还没有提交；界面明确留给 Claude。用户要求先把界面补全，再接着做。

  1. 先提交 Claude 的暂存工作（`275833b`）；

- 集成后全部 505 项测试通过，其中包括 ChatGPT 运行时跳过的桌面测试。

## 2. 界面（只读，不批准规则、不运行实验、不改模型）

**调查页**：如果任务有业务实验调查，显示一个面板：

- 后端交付门禁的结论（可以交付 / 交付被阻止），以及每条阻止原因（中文）；
- 假设账本：与观察相符（不等于已证明）/ 已排除（在声明的实验范围内）/ 尚未检验，每条附支持或反驳它的检查、预测、实际结果和原始记录数；
- 每项实验检查的状态和结果；
- 下一项最能区分假设的检查；
- 原始实验记录 ID（可折叠）和代码版本；
- 结构分析被截断时给出提醒。

面板里固定写明：结论只在已声明的受控场景内成立；没有声明运行时追踪覆盖；结构上的共同上游只是线索。为避免频繁重新校验原始证据，面板最多每 3 秒刷新一次，而且只在状态变化时才重建。

**Agent 集群页**：显示

- 持续推演是否开启、集群规模和上限（调高上限不会自动创建 Agent，也不会替用户选模型）、最近的推演周期；
- 已注册的实验场景、用户已批准的业务规则（只能由用户批准）；
- 安全边界：首脑只能规划和调度；实验代码在本进程内运行，取消是协作式的。

**修复：用户截图里那个游离的小窗口**

- 原因：耦合图谱页的风险列表每次创建最多 60 个"高 / 中"标签。标签在被放进布局之前就被设成可见，而在 Windows 上，没有父窗口的可见控件会成为独立的小窗口（只有图标、还原和关闭按钮）。如果界面线程正忙，它就会留在屏幕上。
- 修复：标签在有父控件之前只记录"想要的可见状态"，放进布局后再生效。
- 用追踪工具验证，游离窗口从 60 个降到 0 个，并加了回归测试。

**耦合图谱页改为后台读取数据**：大项目（用户的 game 项目有 13k 个节点、57k 条边）在界面线程上读取图谱要 1.6 秒以上，弱机器上更久。现在在后台线程读取，读完再在界面线程上绘制。

## 3. ChatGPT 协议审查（针对 `b892275`）——三项全部修复

| 编号 | 问题 | 修复 |
|---|---|---|
| R1 (P1) | 绑定检查被跳过时，仍能输出 accepted | 两种 accepted 状态都要求每条证据的 exists 和 integrity 为 pass，binding 为 pass 或 not_checked |
| R2 (P1) | 等待窗口被跳过，或窗口还没结束时，就判定"确定未发生" | `window_elapsed` 必须是 pass；新增语义规则 `ABSENT_BEFORE_WINDOW_END`（判定时间不能早于窗口结束）；`clock_skew_bounded` 只有写明理由才能为 not_applicable |
| R3 (P2) | 代码证据 ID 和 file/symbol 实体接受绝对路径和 `..` | 统一的仓库路径规则：拒绝开头的 `/`、盘符、`.` 和 `..` 段（包括百分号编码后的 `%2e`） |

ChatGPT 的复现脚本 `reproduce_review.py --assert-rejected`：10 个反例全部被拒绝，退出码 0。新增 5 个无效样本，每个都写明失败原因。

## 4. ChatGPT 运行时审查（针对 `4a74a7d`）——逐项结论

ChatGPT 的回归包已放进 `tests/daemon/test_review_runtime.py`，11 项全部通过。

| 编号 | 问题 | 在当前代码上 | 处理 |
|---|---|---|---|
| R1 | 敏感级别没有随召回、消息传播 | 汇总笔记已在 M6 修复；召回和消息仍有问题 | 召回时按 Agent 模型服务允许的级别过滤（超出的不给，并说明给了几条、为什么）；被采用的笔记会把任务级别提高到它们的级别；`send_message` 带上发送者的级别 |
| R2 | 取消后仍执行工具 | ChatGPT 做业务集群时已加上检查 | 已有，测试通过 |
| R3 | 重启后任务一直停在"运行中" | 早已由中断恢复机制修复 | 测试通过 |
| R4 | 日志还原不了被删减的请求 | M5 已修复（日志记录被改写的内容和工作记忆） | 测试改成新格式，并且逐次验证**每一次**请求都能精确还原 |
| R5 | 上下文预算不是硬上限 | 存在；而且工具说明（约 2,200–3,600 token）根本没有计入 | 工具说明计入预算；删减后仍放不下就不发送，以"预算"原因停止，并说明系统提示 + 工具、任务 + 召回、对话各占多少 |
| R6 | 笔记来源只校验格式 | 存在 | 写入时来源必须真实存在；笔记来源不能是别人的私有笔记；笔记继承来源中最严格的级别 |

**R5 带来的实际影响**：本地小模型的上下文常常只有 2k–4k，仅系统提示加工具说明就要约 3.3k token。以前这种请求会被悄悄超额发送；现在会直接说明放不下。对本地模型，需要把 `context_budget_tokens` 设成模型真实的上下文长度。另见 ADR 0008 末尾的更正。
